# ConfHub 需求边界

本文记录已经逐项确认的第一版需求边界，关键架构见 [architecture.md](architecture.md)。本文为第一版需求基线；后端实现与验证状态见 [backend-implementation.md](backend-implementation.md)，性能目标尚未压测。

## 产品目标

- 使用 Go 开发服务端，使用 React 开发管理界面，定位为轻量、低资源占用的配置中心。
- 提供配置版本管理；版本号由系统自动生成，使用递增整数。
- 支持配置即时获取和变化通知；即时获取使用 HTTP GET，通知使用 WebSocket 并推送完整配置及版本或删除状态。
- 管理界面符合常规操作习惯，支持版本 diff、常见配置格式高亮及 JSON、YAML 手动格式化。
- 支持 PostgreSQL、MySQL 等常见数据库作为存储后端。
- 支持高可用部署；多个实例都能够提供配置管理入口。
- 配置修改后，长连接客户端应能在毫秒级获得新配置；计时边界和验收负载见性能目标。
- 除长连接相关状态外，实例尽量无状态，以便横向扩展。
- 客户端连接时可提供额外标签，作为灰度发布的依据。
- 提供 IP、主机名等常见标签，由 SDK 采集，可显式指定；标签用于分流，不作为可信身份。
- 灰度发布允许按客户端标签使用规则独立的临时内容；回退只适用于主版本。
- 可设置主版本历史保留数量，默认 100；灰度临时内容不进入历史、不占历史配额。
- 减少服务自身的启动配置，使用命令行 flag 和环境变量传入；不使用服务启动配置文件。
- 提供 Docker 镜像和 Docker Compose 部署。
- 提供 Go 和 Python 客户端 SDK。
- 参考 AgileConfig 和 Nacos 的配置管理体验；第一版不兼容既有 Nacos 协议或 SDK。

## 产品边界

- 开发独立配置中心，参考现有产品的使用体验；第一版不兼容 Nacos 现有协议或 SDK。
- 第一版不包含服务注册发现、AI 和配置内容的密钥托管。
- 配置采用 Namespace / Group / 配置名三级结构，参考 Nacos；一份配置是完整文本，以整份文本管理版本。
- 只保证单份配置的原子发布；不提供多份配置同时生效的发布包。
- 管理界面采用用户名密码登录，系统初始化时可以通过启动参数或环境变量传入默认 admin 密码。
- 客户端第一版无需鉴权：客户端配置获取与订阅不通过访问令牌授权。管理操作仍需登录。
- 第一版只提供 admin 管理账户，不实现多用户或项目权限；提供版本操作信息和结构化操作日志。
- 首次初始化必须传入初始 admin 密码，初始化后可在管理界面修改密码。重启时不再用启动参数覆盖已保存的密码。
- 最小高可用部署只强制依赖服务实例和数据库，不强制依赖 Redis、消息队列或其他协调组件。
- PostgreSQL 和 MySQL 均为正式支持的存储后端，产品行为一致；数据库自身高可用由部署环境提供。

## 配置组织、发布和交互

### 配置组织

- Namespace 和 Group 的业务含义由使用者自行决定，不强制绑定环境、团队或应用。
- 提供默认 public 命名空间和 DEFAULT_GROUP 分组。
- 同一 Namespace、Group 内的配置名唯一。

### 保存与全量发布

- 普通配置保存成功即发布，让未命中灰度规则的客户端使用新版本。
- 普通保存不改变规则独立的灰度临时内容，命中规则的客户端继续使用当前 beta。
- 不采用先保存未发布草稿、再单独全量发布的普通编辑流程。
- 每条新灰度规则在创建时复制当前全量内容，名称固定为创建来源主版本号加 beta，例如 V4-beta。后续编辑覆盖该规则的临时内容，全量与其他规则内容保持不变。
- 每份配置的主版本从 1 开始递增；全量保存、全量回退和灰度转全量消耗主版本号。灰度创建与编辑不占用编号、不保存修改历史；主历史内容不可修改。
- 全量回退以历史主版本内容创建下一个主版本并立即全量发布；灰度内容保持不变。
- 每个版本具有描述字段。普通版本由操作人填写，可以为空；自动产生的回退版本在描述中注明回退来源。
- 全量、灰度保存和全量回退均展示 diff 及影响范围，确认后才提交。
- 不提供灰度回退。关闭规则停止该规则生效，并保留内容以便重新开启；删除规则清除对应临时内容。
- 灰度转全量读取选定规则当前的临时内容，生成下一个主版本；规则及临时内容继续保留，由用户决定是否关闭。正文和格式与当前全量一致时不产生重复版本。

### 灰度规则与标签

- 一条规则内的标签条件使用 AND；第一版支持等于和属于指定值集合。
- 需要 OR 时建立多条规则；第一版不支持正则、脚本或百分比随机分流。
- 规则按列表顺序匹配，第一条命中即生效；未命中则使用当前全量版本。
- 管理界面支持规则排序和标签试算，显示命中规则及最终版本。
- 规则支持新增、修改条件、排序、停用和删除，不提供绑定历史或切换目标版本。规则独立拥有 beta，同源创建的多个 beta 通过规则名称区分。这些操作确认后立即生效，并通过乐观锁防止并发覆盖。
- 规则变更后重新计算在线客户端的有效版本。规则停用或删除后继续匹配后面的规则，全部未命中才使用全量版本。
- SDK 自动采集客户端本机 IP 和主机名，允许显式指定以适配多网卡与容器；服务端观察到的连接来源地址另外记录。
- 内置标签名称为 sys.ip、sys.hostname，自定义标签不能占用这些名称。
- 客户端标签用于分流，不作为可信身份依据。

### 编辑和版本对比

- 编辑时不展示 diff；点击保存后展示 diff，操作人确认后才提交保存与发布。
- 普通保存默认对比当前全量，支持选择其他主历史版本作为比较对象；灰度保存只对比当前 beta 与本次编辑，不提供其他版本选择。
- 首次创建展示空内容到新内容的 diff，确认后才保存发布。
- 提供独立的主版本历史列表，可查看正文、进行版本 diff 和全量回退；不显示 beta 编辑历史或灰度回退目标。
- 支持 JSON、YAML、TOML、XML、Properties、INI 和纯文本高亮；先提供 JSON、YAML 的手动格式化，可撤销。
- 声明为结构化格式时，语法错误阻止保存发布；纯文本不做语法校验。YAML 格式化造成的注释或排版变化也进入保存 diff。

## 版本维护与客户端行为

- 使用乐观锁防止并发覆盖。编辑基于的版本发生变化时，拒绝直接保存，保留编辑内容并要求重新对比、确认。
- 选择其他历史版本作为 diff 对象，不改变并发保存校验的基准。
- 正文和格式与当前目标一致时，全量保存不产生新版本。灰度正文、格式或描述变化会覆盖临时内容；仅改描述不通知客户端。正文按原始文本比较，空格或换行变化也算修改。
- 默认保留最近 100 个主版本及当前全量目标。beta 来源编号仅表示创建来源，不引用、不保护对应历史，主历史清理不影响任何 beta 内容。
- 历史和日志由取得数据库短期租约的后台任务分批清理，不固定维护主实例；历史数量允许短暂多出等待清理的版本，完成后满足保留策略。
- 主历史列表标识当前全量；其他旧主版本可按保留策略清理。
- SDK 连接中断或服务故障时保留最后成功获取的配置并自动重连；提供可选磁盘缓存，支持重启后离线读取。
- 首次启动无法连接且没有可用缓存时，SDK 明确返回错误，由应用决定是否终止启动。
- SDK 支持多个服务地址并自动故障切换。
- 订阅保证正常连接和重连后收敛到当前应生效状态，允许跳过快速连续发布的中间版本。
- 配置身份、有效版本、命中规则、正文、格式或存在状态变化时触发回调；未受影响的客户端不触发回调。同名 beta 覆盖和灰度切换可能保持或降低版本号，SDK 不能仅依据版本号判断变化。
- SDK 提供获取、订阅、取消订阅与关闭，返回原文、版本、格式及在线或离线缓存来源。应用通过回调应用配置，不提供框架自动注入或配置合并。
- Go SDK 使用 context；Python SDK 提供同步和 asyncio 接口，异步调用及回调不能阻塞应用 event loop。

## 删除与操作记录

- 第一版不提供回收站。删除配置是永久删除，连同其全部版本和灰度规则一并删除，界面明确提示并要求二次确认。
- 非空 Namespace、Group 不允许直接删除。
- 客户端收到明确删除结果后清除对应内存和磁盘缓存，触发删除回调；后续读取返回不存在，由应用决定如何处理。
- 删除后重新创建同名配置视为新配置，不能误用旧配置的版本身份或缓存。
- 版本列表记录创建时间、操作类型、版本描述和回退来源。
- 保存、回退、规则变更、删除、登录和密码修改写入结构化操作日志，不记录密码或配置正文。
- 第一版不单独建设审计查询界面。

## 规模与性能目标

这些是保留供后续验证的设计目标，并非已经通过验证的性能承诺。当前阶段不编写、执行或展开压测流程。

- 3 个服务实例，共 10,000 个客户端长连接。
- 每实例空载 RSS 不超过 64 MiB；上述负载下 RSS 不超过 256 MiB。数据库资源单独计算。
- 同一内网正常运行时，从发布事务提交到目标 SDK 获得新内容，延迟 P99 不超过 300 ms。
- 故障、重连和网络分区的恢复指标单独定义。
- 支持 10,000 份配置，单份最大 1 MiB；每个客户端最多订阅 10 份配置。
- 后续常规发布验证负载：配置不超过 10 KiB，每次影响不超过 1,000 个客户端，持续每秒 10 次发布。
- 后续小配置广播验证负载：配置不超过 1 KiB，每次影响全部 10,000 个客户端，每秒 1 次发布。
- 两组负载都以 P99 不超过 300 ms 为目标。大配置和更高负载不套用相同延迟目标。
- 保留的环境基线为服务节点各 4 vCPU、1 GiB 可用内存，数据库 4 vCPU、8 GiB、SSD，网络 1 Gbps、RTT 不超过 1 ms；数据库与负载生成器独立部署。正式测量细节留到后续阶段。

## 实现与部署约束

- 服务端使用 Gin；前端使用 React、TypeScript、Vite、CodeMirror 6。
- React 构建目录复制进同一个应用镜像，由 Go HTTP 服务直接提供，不嵌入 Go 可执行文件。
- 使用 golang-migrate/migrate 管理 PostgreSQL、MySQL 的版本化迁移。此次灰度模型使用 schema 2，只支持空数据库初始化；不兼容 schema 1 配置数据，也不自动清除旧数据库。
- 提供 Docker Compose 部署；数据库持久化，多实例共享数据库和 JWT 签名密钥，SDK 可使用多个服务地址。
