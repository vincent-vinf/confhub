# 压测方案与运行指南

压测使用生产 Dockerfile 构建 Go/React 镜像，通过独立 Docker Compose 项目启动 PostgreSQL 和三个应用实例。负载程序使用公开 HTTP API 与正式 Go SDK；服务端关闭 race/coverage，正式负载生成器也关闭 race。每个客户端维持一条 WebSocket、订阅一份配置。

当前默认应用 1C/1GiB、PostgreSQL 1C/2GiB 档位下，分别通过了 5 分钟的 20,000 GET/s、150 次主版本发布/s、10,000 客户端广播和灰度混合负载验证。广播短测最高通过 12,000 客户端，混合短测通过 15,000，空闲连接最高测到 20,000；25,000 GET/s 长测因生成器未提交比例超预算未通过。首轮小内存档位及所有未通过记录作为对照保留，具体条件见文末。

## 资源档位

部署模板 `compose.yaml`、`compose.mysql.yaml` 以及压测模板使用相同默认限制：

| 容器 | CPU 上限 | 内存上限 | 交换空间 |
| --- | --- | --- | --- |
| 每个应用实例 | 1 vCPU | 1 GiB | 禁用额外 swap |
| 数据库 | 1 vCPU | 2 GiB | 禁用额外 swap |

通过 `CONFHUB_APP_CPUS/CONFHUB_APP_MEMORY/CONFHUB_DB_CPUS/CONFHUB_DB_MEMORY` 修改部署资源。Go 默认设置 `GOMEMLIMIT=768MiB`，通过 `CONFHUB_APP_GO_MEMORY` 调整；它是软目标，给 socket/内核开销留余量，调整容器内存时应一并调整。应用文件描述符上限为 65536。已有容器需重建后才使用新限制。

默认档位已按本轮要求调整为应用 1C/1GiB、数据库 1C/2GiB；首轮 256 MiB 应用档位作为历史对照保留。此前需求中的每应用 4 vCPU/1 GiB、数据库 4 vCPU/8 GiB 基线可以另行指定。容器 CPU 是配额，不是独占 CPU。单机 Compose、宿主机内核、数据库与生成器共享资源，实测结果仅对应报告中的环境；不能当作跨主机网络或专用节点的容量承诺。

## 测试矩阵

每个档位先创建独立配置、完成建连与初始状态验证，预热 5 秒，再持续测量 30 秒。正式容量确认延长到 300 秒。默认步骤递增，某一场景首次失稳后跳过该场景更高档位，保留已知稳定点和首次失稳点。没有失稳则只能说达到最高已测档位，不能称为极限。

| 场景 | 固定条件 | 默认递增负载 |
| --- | --- | --- |
| `get` | 1 KiB 正文、热缓存、无长连接 | 1000、5000、10000、20000 GET/s |
| `idle` | 1 KiB、一配置、无持续发布 | 1000、5000、10000 条真实 SDK 长连接 |
| `fanout` | 1 KiB、同一配置广播、1 次全量发布/s | 1000、5000、10000 客户端 |
| `mixed` | 10 KiB、10 配置、总计 10 次发布/s、500 GET/s | 1000、5000、10000 客户端；每份配置均约 10% 灰度 |
| `write` | 1 KiB、20 配置、无订阅、每配置单个写队列 | 10、50、100、200、500 次发布/s |

混合场景按配置轮转，每五轮包含一轮 beta 修改，其他为全量修改。每条灰度规则匹配同一配置的唯一 beta，全量修改不应通知灰度客户端，beta 修改不应通知普通客户端。GET 使用单独的固定配置，避免将并发发布期间的合法旧值当作读取错误。读吞吐测试验证原始 HTTP 200 和正文，不使用 SDK 离线缓存替代成功请求。

发布覆盖真实格式校验、认证、权限查询、事务、主历史/原位 beta、事件日志与审计写入。配置正文使用指定字节数的纯文本；结构化格式解析成本、冷缓存/一万配置数据集、多订阅、慢消费者、断线风暴、故障恢复压测与 MySQL 不在这次矩阵内。正确性故障回归见 [testing.md](testing.md)。

## 指标与判定

- GET：实际成功请求数、HTTP 状态、错误、未能提交的计划请求、请求耗时和计划到完成的 P50/P95/P99/最大值。默认要求错误与未提交比例不超过 0.1%，计划到完成 P99 ≤100 ms。
- 发布：计划数、实际提交成功数、错误和未提交数，计划到完成 P99 ≤500 ms，错误与未提交比例不超过 0.1%。不同配置可并发，同一配置串行维护编辑基准，避免故意制造乐观锁冲突干扰吞吐结果。
- 通知：每次成功发布预计影响的订阅数量、实际收到数量、未观测数量、错误路由/旧快照数量，发布开始到 SDK 回调的 P50/P95/P99/最大值。默认 P99 ≤300 ms、未观测比例 ≤0.1%，结束后每个订阅必须收敛到最终正确正文及 beta 标识。
- 资源：各应用进程 RSS、容器 working set、CPU、CPU 节流、OOM/退出/重启，以及负载生成器的 CPU 和 RSS。记录整个建连/预热/测量/清理过程的峰值，另统计正式测量区间。OOM、重启、错误快照、最终不收敛均视为失稳。

读写使用按时间调度的开放式负载，不会因响应变慢而自动降低计划请求速率。工作队列满时记录未提交数量；从计划到完成的延迟包含本地排队，避免仅计算成功请求的短延迟而掩盖过载。原始计数和实测区间长度保留在 JSON 中，成功吞吐可由 `ok / duration_seconds` 计算；请求尾部排空时间另有 `elapsed_seconds`。

通知计时在请求发送前开始，使用同一 Go 进程的单调时钟，包含提交前的校验/事务和网络耗时。它是提交到回调时间的保守上界，**不是数据库提交时刻的直接测量**。SDK 回调入口立即取时间，通过有界非阻塞队列异步统计，不把统计锁等待计入延迟；`recorder_dropped` 非零表示采样溢出，该档位无效。发布完成时间也在统计前采集。回调可以早于发布 HTTP 响应，脚本不会丢弃这类样本。P99 同时报告样本数量和覆盖比例：快速发布允许合并通知，因此未观测可能是合并或遗漏；不能仅凭收到的少数快样本宣布达标。最终收敛另行验证。

负载生成器默认 `GOMAXPROCS=2`、`GOMEMLIMIT=2GiB`，后者是 Go 的软内存目标。报告标记测量期生成器接近 CPU 预算的情况。这时需增加生成器资源或在独立机器重新测量，不能将生成器瓶颈称为服务端极限。脚本实际使用轻量预算，不宣称完成此前所有资源与网络设计目标的正式验收。

## 运行方式

需要本机 Linux Docker Unix socket、Docker Compose、Go 1.25 和 Python 3.10+。使用固定 PostgreSQL 镜像 `registry.cn-hangzhou.aliyuncs.com/bodesi/postgres:17`，不需要额外压测工具依赖。

```sh
# 所有场景、默认递增档位：
make load-test
# 或：
python3 tests/load/run.py

# 快速验证脚本；race 仅用于验证生成器正确性，不用于容量数字：
python3 tests/load/run.py --scenarios get,fanout,mixed,write,idle \
  --read-rates 100 --write-rates 5 --connections 20 \
  --mixed-get-rate 50 --duration 5 --warmup 1 \
  --race-generator --require-all-pass

# 细化读吞吐边界；生成器增加到 4 个 Go 调度线程：
python3 tests/load/run.py --scenarios get --read-rates 5000,7500,10000,15000 \
  --generator-procs 4 --duration 60

# 将已测稳定点保持 5 分钟，确认广播和灰度混合负载：
python3 tests/load/run.py --scenarios fanout,mixed --connections 1000 \
  --duration 300 --warmup 10 --require-all-pass

# 按此前较大资源基线测试：
python3 tests/load/run.py --app-cpus 4 --app-memory 1g --go-memory 768MiB \
  --db-cpus 4 --db-memory 8g --generator-procs 4
```

最后一个命令需要足够的宿主机资源，正式比较建议将数据库与生成器移到独立机器。脚本不读取真实 `.env`，不使用部署的 `data/`，创建独立项目、镜像标签、随机 loopback 端口、临时数据库卷及随机凭据；正常、失败或信号中断后清理其所有资源。不会更新正在运行的生产镜像标签或容器。

直接测试单独准备好的压测集群：

```sh
mkdir -p test-results
export CONFHUB_LOAD_ADDRESSES='http://127.0.0.1:8080,http://127.0.0.1:8081,http://127.0.0.1:8082'
export CONFHUB_LOAD_PASSWORD='测试环境管理员密码'
go -C tests/load run . --scenario fanout --clients 1000 --configs 1 \
  --size 1024 --publish-rate 1 --duration 60s --warmup 5s \
  --output ../../test-results/manual-load.json
unset CONFHUB_LOAD_PASSWORD
```

直接模式自行采集远端资源指标，并使用允许压测的独立环境。程序通过管理 API 创建和删除独立 namespace/config，审计记录仍按系统策略保留；SDK 按实例轮转分布，不在客户端静默故障切换掩盖某个实例不可用。

## 报告与退出码

报告目录为被 Git 忽略的 `test-results/load-YYYYMMDD-HHMMSS`，日期使用北京时间。可用 `--report-dir` 指定空目录，不能覆盖旧报告。

- `environment.json`：代码版本、是否有未提交修改、Docker 镜像 ID、实例地址、已核验的 CPU/内存限制、CPU 型号、脚本 SHA256、所有负载参数。
- `summary.json`：每个档位、测量结果、资源峰值、最高已测稳定点、首次失稳点和清理状态。
- 各档位 `load.json`：开放负载计数、延迟分位、通知覆盖、最终收敛、失败原因与清理错误。
- 各档位 `resources.jsonl`：带阶段标记的资源采样；`generator.log`、`containers.log` 和 `build.log` 用于定位失败。

档位不达标是寻找容量边界时的预期结果，默认运行器保留报告并继续其他场景；`--require-all-pass` 在任何档位未通过时返回非零，适合稳定负载的持续回归。基础设施、初始化、清理或采样异常返回非零。直接 Go 程序通过返回 0，负载未达标返回 1，初始化/运行失败返回 2。

## 验证步骤

1. 先以低负载运行五类场景，检查计数、完整通知和资源限制，使用生成器 race 及指标单元测试排除测试本身的数据竞争。
2. 按默认档位递增，保留通过和失败数据，不对失败结果自动重试覆盖。
3. 在最高通过与首次失稳之间细化连接数或请求率；生成器接近 CPU 预算时先增加其资源，重新确定边界。
4. 对建议运行档位做至少 300 秒确认，留出 20%–30% 余量；分别给出能保持连接的规模、满足延迟预算的规模及读写吞吐，避免合并成一个“最大客户端数”。
5. 性能改动后使用相同镜像构建方式、资源、payload、实例分布、轮次和指标口径重复测试，记录差异。

## 2026-10-13 首轮实测：应用 1C/256MiB，PostgreSQL 2C/1GiB

环境：同一台 8 vCPU、约 16 GiB 内存的 Linux 虚拟机（QEMU Virtual CPU version 2.5+，Linux 5.15），生成器使用 4 个 Go 调度线程、512 个 GET 工作协程。三个应用各限制 1 vCPU/256 MiB，`GOMEMLIMIT=192MiB`，PostgreSQL 17 限制 2 vCPU/1 GiB；轮询间隔 100 ms。使用生产 Dockerfile、提交 `152cb86` 加本次未提交改动，所有请求通过 loopback/Compose 网络，未测试跨机器网络。原有应用、数据库与其他容器仍在同一宿主机运行；它们没有被重建，CPU 配额也没有改变。

### 30 秒筛选

以下为修正采样后重测的结果；所有已提交 HTTP 操作均无错误，所有订阅最终收敛，没有 OOM/重启、错误快照或采样溢出。

| 场景 | 通过档位 | P99 | 首个未通过档位与原因 |
| --- | --- | --- | --- |
| 热缓存 GET，1 KiB | 35,000/s；成功 1,049,482/1,050,000，未提交 0.0493% | 计划到完成 11.71 ms | 50,000/s；未提交 36,937/1,500,000（2.46%），P99 21.50 ms |
| 主版本写入，20 配置、1 KiB、无订阅 | 200/s；成功 5,995/6,000，未提交 0.0833% | 计划到完成 49.30 ms | 250/s；未提交 29/7,500（0.387%），P99 62.36 ms |
| 同配置广播，1 KiB、1 发布/s | 8,000 客户端；240,000/240,000 通知 | 发布开始到回调 185.81 ms | 10,000 客户端；300,000/300,000 通知，P99 771.55 ms 超预算 |
| 混合，10 配置、10 KiB、10 发布/s、500 GET/s、约 10% 灰度 | 8,000 客户端 | 通知 139.44 ms；GET 20.18 ms；发布 50.98 ms | 10,000 客户端；通知 804.04 ms、GET 122.01 ms、发布 655.85 ms 均超预算 |
| 空闲长连接 | 10,000 客户端；单实例 RSS 峰值约 208 MiB | 无持续发布，不评估通知 P99 | 最高已测点，未继续寻找连接上限 |

8,000 客户端广播测量期单实例 RSS 峰值约 195 MiB；10,000 客户端广播约 214 MiB，出现接近 CPU 配额的使用量和明显节流。能够保持 10,000 条连接，并不代表在这个资源档位下满足 300 ms 的通知目标。35,000/s 和 200/s 也只是本机短测通过点，不能直接作为生产运行建议：此前另一轮 200/s 已出现 0.267% 未提交，边界附近存在波动。

50,000 GET/s 时应用 CPU 峰值仍低于约 64%，生成器约 284%，失败表现是本地工作队列无法接收所有计划请求，没有服务端 HTTP 错误。这是当前单机、生成器和判定规则下的未通过点，**不能据此断言服务端的绝对读吞吐上限**；进一步确认需要独立机器或多个负载生成器。不同场景数据不可相加。

原始报告（均已清理测试容器、卷、镜像及临时凭据）：

- `test-results/load-20261013-115919`：8,000/10,000 客户端广播和混合重测。
- `test-results/load-20261013-120228`：35,000/50,000 GET/s，175/200 次写入/s。
- `test-results/load-20261013-120629`：250 次写入/s，10,000 条空闲连接。

最初未设置 Go 内存软目标时，10,000 条连接触发过单实例 OOM（`test-results/load-20261013-112014`），因此部署模板增加 192 MiB 软目标，再按相同 256 MiB 硬限制重测，消除了本次重测中的 OOM。早期通知采样将统计锁等待计入延迟；`load-20261013-112559`、`load-20261013-114053` 保留为过程记录，最终通知数字使用上表的回调入口计时结果。

### 300 秒持续确认与建议档位

在短测通过点下保留约 25%–29% 余量，顺序执行四项测量，每项预热 10 秒、正式测量 300 秒。以下为测量期单实例进程 RSS 峰值，CPU 和数据库容器另有独立记录。

| 场景 | 验证负载 | 实际结果 | P99 | 应用 RSS 峰值 |
| --- | --- | --- | --- | --- |
| GET | 25,000/s，1 KiB 热缓存 | 7,495,576/7,500,000 成功；未提交 4,424（0.059%），HTTP 错误 0 | 计划到完成 5.47 ms | 32.2 MiB |
| 主版本写入 | 150/s，20 配置，无订阅 | 45,000/45,000 成功；未提交和错误均为 0 | 计划到完成 32.89 ms | 24.9 MiB |
| 广播 | 6,000 客户端，1 KiB，1 发布/s | 300/300 发布；1,800,000/1,800,000 通知 | 通知 171.79 ms；发布 53.03 ms | 193.6 MiB |
| 灰度混合 | 6,000 客户端，10 配置，10 KiB，10 发布/s、500 GET/s，约 10% 灰度 | 3,000/3,000 发布，150,000/150,000 GET，1,332,000/1,332,000 通知；无未提交或错误 | 通知 96.77 ms；GET 10.65 ms；发布 26.05 ms | 197.4 MiB |

四项均满足上述判定规则；全部订阅最终收敛，采样队列没有溢出，容器没有 OOM/重启。空载两次采样中应用 RSS 约 19–20 MiB；长测数据库 working set 峰值约 244 MiB。这里只对各自的 5 分钟负载给出通过结论，不能推断无期限持续运行或同时叠加四项负载时仍有相同容量。

首轮 256 MiB 应用资源档位下建议先以 **6,000 条连接的已测通知负载**作为部署规划参考，读多或集中写入另参考上述独立场景。需要满足 10,000 条连接及 300 ms 通知预算时，应增加应用 CPU/内存后按同样口径复测；此次 1 vCPU/256 MiB 档位未通过该组合目标。多订阅、冷缓存、更大配置、跨主机网络或不同数据库均需独立验证。

复现本次持续确认：

```sh
python3 tests/load/run.py --scenarios get,write,fanout,mixed \
  --read-rates 25000 --write-rates 150 --connections 6000 \
  --workers 512 --generator-procs 4 --duration 300 --warmup 10 \
  --app-memory 256m --go-memory 192MiB --db-cpus 2 --db-memory 1g \
  --require-all-pass
```

原始报告：`test-results/load-20261013-120801`，四项 `stable=true`、`valid_metrics=true`，运行器返回 0，`cleanup=true`、清理与采样错误列表为空。报告包含脚本 SHA256、镜像 ID、完整参数和逐秒资源记录。测试创建的容器、卷、镜像和 `.env` 已清理，保留原始报告、二进制和容器日志用于复核；报告目录被 Git 忽略。

脚本指标单元测试与 `go test -race`、`go vet`、Python Ruff 检查通过；小规模真实集群验证涵盖全部五类场景，并通过生成器 race 检查。PostgreSQL/MySQL Compose 的三个应用及数据库 CPU、内存、swap 和应用文件描述符限制均已核验；MySQL 只核验部署模板，未运行实际 MySQL 压测。

## 2026-10-13 第二轮：应用 1C/1GiB，PostgreSQL 1C/2GiB

保持三个应用实例、100 ms 轮询、相同宿主机、生产构建方式、SDK、payload、负载与判定口径。各应用内存上限从 256 MiB 增至 1 GiB，Go 软目标从 192 MiB 增至 768 MiB；PostgreSQL 内存从 1 GiB 增至 2 GiB，CPU 从 2 vCPU 降至 1 vCPU。Docker 实际限制已核验。原有运行中服务未重建，本轮使用独立临时集群。

### 30 秒重新筛选

| 场景 | 通过档位 | P99 | 首个未通过档位与原因 |
